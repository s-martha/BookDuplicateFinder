# PROJECT_SPEC.md

## 1. Назначение проекта

**BookMatch** --- многопоточный движок поиска похожих текстовых
документов с инкрементальной индексацией. Первое практическое применение
--- поиск дубликатов электронных книг в локальной библиотеке, даже если
файлы имеют разные названия, метаданные, форматы или небольшие различия
в тексте.

Проект предназначен для портфолио C++-разработчика. Приоритеты:
современный C++, алгоритмы поиска сходства, многопоточность, корректное
управление ресурсами, тестирование, измеримая производительность и
понятная архитектура.

### Основные принципы

-   **Никаких изменений пользовательских файлов.** BookMatch только
    читает исходные документы. Не удаляет, не переименовывает и не
    перемещает их.
-   **Результаты воспроизводимы.** Для алгоритмов и параметров
    используются явно заданные настройки и seed, если он необходим.
-   **Ошибки отдельных файлов не останавливают всю индексацию.**
-   **Оценка сходства не равна гарантии дубликата.** Отчёт должен
    показывать показатель сходства и позволять пользователю
    самостоятельно проверить результат.
-   **Простая базовая реализация нужна для сравнения.** LSH не должен
    быть единственным способом проверки качества: на небольших наборах
    должен быть доступен полный перебор пар.
-   **Не добавлять технологии ради технологий.** На первом этапе это
    CLI-приложение, а не веб-сервис.

## 2. Цели и критерии успеха

### Цели

1.  Рекурсивно находить поддерживаемые документы в одной или нескольких
    папках.
2.  Извлекать текст из распространённых книжных форматов.
3.  Нормализовать текст для устранения несущественных различий
    оформления.
4.  Находить точные дубликаты файлов, одинаковый нормализованный текст и
    приблизительные дубликаты.
5.  Хранить индекс между запусками и повторно обрабатывать только новые
    или изменившиеся файлы.
6.  Использовать ограниченный пул рабочих потоков для параллельной
    обработки.
7.  Формировать отчёт о группах дубликатов и отдельных парах-кандидатах.
8.  Измерять качество поиска и ускорение при разном количестве потоков.

### Критерии успеха MVP

-   Проект собирается на Linux с помощью CMake.
-   Есть понятный CLI и инструкция по установке/запуску.
-   Тесты покрывают нормализацию, шинглы, сравнение, группировку и
    ключевые компоненты многопоточности.
-   Индексация продолжает работу, если отдельный файл повреждён или
    формат не поддерживается.
-   Повторный запуск не извлекает заново текст неизменённых файлов, если
    исходный файл и версия настроек извлечения не изменились.
-   Отчёт не содержит выдуманных результатов: метрики сходства
    вычисляются алгоритмом и объясняются в документации.
-   Есть воспроизводимый benchmark для 1, 2, 4 и 8 потоков (если машина
    поддерживает такое число потоков).
-   В README описаны архитектура, ограничения, примеры использования и
    измеренные результаты.

## 3. Целевая платформа и технологии

-   Язык: **C++20**.
-   Сборка: CMake.
-   ОС первого приоритета: Linux (Ubuntu); код по возможности не должен
    быть привязан к Linux.
-   Стандартная библиотека: STL, `std::filesystem`, `std::jthread`,
    `std::mutex`, `std::condition_variable`, `std::stop_token`.
-   База индекса: SQLite.
-   Извлечение текста из форматов: внешняя утилита Calibre
    `ebook-convert` для поддерживаемых ею форматов; отдельные адаптеры
    для форматов, которые удобнее обрабатывать напрямую.
-   Тесты: GoogleTest или Catch2 --- выбрать один фреймворк и не
    подключать оба без причины.
-   CI: GitHub Actions для сборки и запуска тестов на Linux.
-   Отчёты: CSV как обязательный формат; человекочитаемый текстовый
    вывод CLI. HTML-отчёт --- необязательное расширение.
-   Сторонние зависимости должны быть перечислены в README и по
    возможности подключаться через стандартный механизм CMake.

Не писать собственные парсеры всех книжных форматов. Внешние процессы
запускать безопасно: не строить shell-команды конкатенацией
пользовательских строк; проверять код завершения, ограничивать время
выполнения, собирать stderr и корректно обрабатывать отсутствующую
утилиту.

## 4. Поддерживаемые форматы

Основные пользовательские форматы:

-   FB2
-   EPUB
-   PDF
-   TXT
-   DOCX
-   DJVU
-   MOBI

Могут встречаться и другие форматы. Архитектура должна позволять
добавлять новые извлекатели без переписывания алгоритмов сходства.

### Требования к извлечению

1.  Извлекать текст в промежуточное представление UTF-8.
2.  Разделять ошибки: неподдерживаемый формат, ошибка запуска
    извлекателя, тайм-аут, повреждённый файл, пустой результат,
    отсутствие текстового слоя.
3.  Сохранять исходный путь и метаданные файла отдельно от извлечённого
    текста.
4.  Не считать отсутствие текста доказательством отсутствия дубликата.
5.  Для сканированных PDF/DJVU без текстового слоя сообщать, что
    требуется OCR. Встроенный OCR **не входит в MVP**.
6.  Проверять размер и тип результата; не загружать весь корпус
    документов одновременно в память.
7.  Не доверять расширению файла без проверки результата извлечения.
8.  Для Calibre задать ограничение на число одновременно работающих
    процессов, тайм-аут и диагностические сообщения.

Извлечение текста --- отдельный слой системы. Алгоритмы сравнения не
должны зависеть от конкретного формата файла.

## 5. Нормализация текста

Реализовать документированную и тестируемую нормализацию. Базовый
профиль должен:

-   декодировать текст в UTF-8;
-   приводить Unicode к согласованной форме нормализации, если доступна
    подходящая библиотека;
-   приводить текст к нижнему регистру с корректной обработкой Unicode;
-   унифицировать пробельные символы;
-   удалять или унифицировать пунктуацию для построения токенов;
-   по настройке приводить `ё` к `е`;
-   разбивать текст на последовательность слов-токенов;
-   не включать в сравнение случайные различия форматирования.

Не удалять автоматически все короткие слова и не использовать
агрессивную лемматизацию в базовом профиле: это может ухудшить
различение разных произведений.

По возможности сохранять и нормализованный текст, и токены/сигнатуры
отдельно. Изменение параметров нормализации должно инвалидировать
соответствующие индексные данные. В отчёте или диагностике должна быть
возможность понять, какие настройки использовались.

## 6. Алгоритмы обнаружения дубликатов

Система должна реализовывать несколько уровней, чтобы сравнивать их
качество и производительность.

### Уровень A --- идентичные файлы

-   Вычислять SHA-256 исходного файла.
-   Использовать совпадение SHA-256 как признак побайтового совпадения.
-   Не использовать один лишь размер файла как доказательство
    совпадения.

### Уровень B --- одинаковый нормализованный текст

-   Вычислять криптографический хеш нормализованного текста.
-   Если хеш совпал, считать документы кандидатами на точное совпадение
    нормализованного текста.
-   При необходимости подтверждать совпадение сравнением самого
    нормализованного текста, а не полагаться исключительно на хеш.

Это помогает находить одинаковый текст в разных форматах и с разными
метаданными.

### Уровень C --- приблизительное сходство

-   Токенизировать нормализованный текст.
-   Строить шинглы из последовательностей соседних слов; размер шингла
    должен быть настраиваемым (начальное значение --- 5 слов).
-   Вычислять MinHash-сигнатуру на основе детерминированных 64-битных
    хешей.
-   Использовать LSH для генерации пар-кандидатов, не выполняя полный
    перебор на больших коллекциях.
-   Для кандидатов вычислять более точные показатели сходства, включая
    Jaccard similarity множеств шинглов и отношение объёмов текстов.
-   По возможности учитывать порядок/покрытие совпадающих фрагментов,
    чтобы отличать почти одинаковые полные книги от частичных
    совпадений.

Не заявлять, что MinHash/LSH гарантированно обнаруживает все пары. LSH
допускает пропуски и ложные кандидаты; параметры должны быть
настраиваемыми и проверяемыми.

### Базовая проверка полным перебором

Добавить режим полного перебора всех пар для небольших корпусов и
тестовых наборов. Он нужен как контрольная точка для оценки полноты LSH.
Для `N` документов число пар равно `N * (N - 1) / 2`.

### Порог и классификация результатов

Порог приблизительного сходства задаётся пользователем. Значение по
умолчанию должно быть задокументировано и считаться стартовой
настройкой, а не универсальной границей.

Результаты желательно классифицировать как: - точное совпадение файла; -
совпадение нормализованного текста; - вероятный дубликат; - частичное
совпадение / требует проверки.

Не объединять документы в одну группу только потому, что цепочка парных
совпадений транзитивно связала их: группировка должна учитывать риск
того, что A похож на B и B похож на C, но A не похож на C. Выбранная
стратегия группировки должна быть описана и покрыта тестами.

Разные переводы одного произведения и сильно переработанные редакции не
входят в гарантируемые случаи обнаружения. Семантическое сопоставление и
межъязыковой поиск --- будущие расширения.

## 7. Многопоточность

Реализовать фиксированный пул рабочих потоков на C++20. Предпочтительно
использовать `std::jthread` и механизмы остановки C++20, если это
упрощает корректное завершение.

### Требования

-   Число рабочих потоков задаётся CLI; значение по умолчанию выбирается
    разумно на основе доступных аппаратных потоков.
-   Не создавать отдельный поток на каждый файл.
-   Использовать ограниченную очередь задач или иной механизм
    backpressure, чтобы не накапливать неограниченное количество заданий
    и текстов в памяти.
-   Обеспечить безопасное завершение, в том числе при ошибках и отмене.
-   Исключения из рабочих задач должны перехватываться на границе задачи
    и преобразовываться в статус ошибки конкретного документа;
    необработанное исключение не должно завершать процесс.
-   Счётчики и состояние индекса должны обновляться потокобезопасно.
-   Избегать глобальной блокировки вокруг всей обработки документа.
-   Не выполнять конкурентные записи в SQLite через одно соединение.
    Предпочтительна схема с одним writer-потоком/соединением и передачей
    ему результатов либо другая явно обоснованная стратегия.
-   Чётко определить владельца данных и время жизни задач; избегать
    гонок и висячих ссылок.
-   Ограничивать параллельный запуск внешних извлекателей независимо от
    числа рабочих потоков.

Параллелить прежде всего извлечение, нормализацию и построение сигнатур.
Отдельно измерить, имеет ли смысл параллелить этап сравнения на целевом
объёме данных.

## 8. Инкрементальная индексация и SQLite

Индекс должен сохраняться между запусками.

Хранить как минимум:

-   канонический путь к файлу;
-   размер и время последнего изменения;
-   SHA-256 исходного файла;
-   формат/тип извлекателя и статус обработки;
-   версию/параметры нормализации;
-   хеш нормализованного текста;
-   число токенов и базовые статистики;
-   MinHash-сигнатуру и необходимые данные LSH;
-   время последней успешной индексации и текст ошибки, если она была.

### Правила обновления

-   Новый файл --- добавить в индекс.
-   Изменённый файл --- переиндексировать.
-   Неизменённый файл с актуальной версией настроек --- пропустить.
-   Исчезнувший файл --- пометить отсутствующим или удалить из активного
    индекса по согласованной политике; не удалять сам файл на диске.
-   Изменившиеся настройки нормализации или алгоритма, влияющие на
    результаты, должны инициировать нужную переиндексацию.
-   Изменение корневых папок не должно случайно приводить к удалению
    данных вне просканированной области.

Обновление индексных данных должно быть транзакционным, чтобы прерывание
процесса не оставляло полузаписанную запись. Предусмотреть версию схемы
БД и механизм миграций или контролируемого пересоздания индекса.

Не хранить без необходимости несколько полных копий текста в памяти. В
БД можно хранить нормализованный текст или токены, если это необходимо
для точной проверки, но решение должно учитывать объём данных и
объясняться в README.

## 9. CLI

Минимально поддержать следующие команды:

``` text
bookmatch index <dir> [<dir> ...] [--threads N]
bookmatch duplicates [--threshold VALUE] [--method lsh|bruteforce]
bookmatch compare <file1> <file2>
bookmatch stats
```

Допустимо скорректировать синтаксис в ходе реализации, если он остаётся
согласованным и документированным.

### `index`

-   Рекурсивно сканирует переданные каталоги.
-   Показывает прогресс и сводку: найдено файлов, обработано, пропущено
    по кешу, ошибки.
-   Не падает целиком из-за одного плохого документа.
-   Поддерживает настройку числа потоков.

### `duplicates`

-   Выводит группы и пары найденных совпадений.
-   Показывает пути, тип совпадения, оценку сходства и полезные
    показатели.
-   Позволяет выбрать LSH или полный перебор.
-   Поддерживает экспорт в CSV.
-   Ничего не удаляет и не изменяет в исходной библиотеке.

### `compare`

-   Сравнивает две указанные книги.
-   Показывает, удалось ли извлечь текст, число токенов, тип совпадения
    и показатели сходства.
-   Даёт понятное сообщение, если формат не поддерживается или
    извлечение не удалось.

### `stats`

-   Показывает число активных/отсутствующих документов, количество
    ошибок, распределение по форматам и состояние индекса.
-   Если доступны измерения, показывает время последней индексации и
    статистику кеша.

Ошибки использования должны выводить краткую справку и возвращать
ненулевой код завершения. Формат вывода, подходящий для скриптов, не
должен смешиваться с диагностическими сообщениями; по возможности
предусмотреть отдельный CSV-экспорт.

## 10. Архитектура кода

Разделить проект на небольшие модули с явными обязанностями. Возможная
структура:

``` text
BookMatch/
├── CMakeLists.txt
├── README.md
├── PROJECT_SPEC.md
├── .gitignore
├── cmake/
├── include/
│   └── bookmatch/
│       ├── cli/
│       ├── core/
│       ├── extraction/
│       ├── text/
│       ├── similarity/
│       ├── concurrency/
│       ├── storage/
│       └── reporting/
├── src/
│   ├── main.cpp
│   ├── cli/
│   ├── core/
│   ├── extraction/
│   ├── text/
│   ├── similarity/
│   ├── concurrency/
│   ├── storage/
│   └── reporting/
├── tests/
│   ├── unit/
│   ├── integration/
│   └── fixtures/
├── benchmarks/
└── docs/
    └── architecture.md
```

Это ориентир, а не требование создавать пустые файлы и каталоги заранее.
Структуру следует адаптировать по мере появления реальных модулей.

Рекомендуемые логические компоненты:

-   `FileScanner` --- обход каталогов и обнаружение файлов.
-   `TextExtractor` --- общий интерфейс извлечения текста.
-   `CalibreExtractor` и `PlainTextExtractor` --- конкретные реализации.
-   `TextNormalizer` и `Tokenizer`.
-   `Shingler`, `MinHasher`, `LshIndex`.
-   `SimilarityCalculator` --- точные метрики сравнения.
-   `ThreadPool` / pipeline --- планирование задач и backpressure.
-   `IndexRepository` --- операции SQLite.
-   `DuplicateFinder` --- поиск кандидатов и классификация.
-   `ReportWriter` --- вывод в терминал и CSV.

Избегать чрезмерной абстракции. Интерфейсы вводить там, где они
позволяют заменять извлекатели, алгоритмы или хранилище, а не ради
формального ООП.

## 11. Тестирование

Использовать небольшие искусственные тексты и безопасные фикстуры, не
включающие защищённые авторским правом полные книги.

### Unit-тесты

-   Нормализация регистра, пробелов, пунктуации и `ё/е` согласно
    настройкам.
-   Корректная токенизация UTF-8 текста на русском и английском.
-   Построение шинглов, в том числе для коротких текстов.
-   Детерминированность MinHash при одинаковых настройках.
-   Jaccard similarity на известных множествах.
-   LSH находит очевидные пары-кандидаты на специально подготовленных
    данных.
-   Пустые документы и документы с недостаточным количеством токенов
    обрабатываются явно.
-   Группировка не объединяет заведомо несходные документы через слабую
    цепочку совпадений.

### Integration-тесты

-   Индексация папки с разными форматами при наличии и отсутствии
    Calibre.
-   Ошибка одного файла не прерывает обработку остальных.
-   Повторная индексация пропускает неизменённые файлы.
-   Изменённый файл переиндексируется.
-   Исчезнувшие файлы корректно отражаются в индексе.
-   SQLite восстанавливает согласованное состояние после
    прерывания/ошибки.
-   Параллельная индексация даёт те же логические результаты, что и
    однопоточная.
-   Корректное завершение пула потоков при пустой очереди, ошибке и
    запросе остановки.
-   CSV-отчёт корректно экранирует запятые, кавычки и Unicode-пути.

Добавить тесты с контролируемыми изменениями: перестановка пробелов,
пунктуация, изменение метаданных, добавление предисловия, небольшие
вставки/удаления текста, разные форматы одного текста, разные тексты
одного автора и книга, включённая в более крупный сборник.

## 12. Производительность и качество

Создать воспроизводимый benchmark, который измеряет отдельно:

-   время сканирования;
-   время извлечения;
-   время нормализации и построения сигнатур;
-   время поиска кандидатов;
-   время точной проверки;
-   пиковую или приблизительную память, если это возможно надёжно
    измерить на платформе;
-   общее время индексации.

Сравнить 1, 2, 4 и 8 потоков на одном и том же наборе данных. Указывать
размер и состав корпуса, оборудование, параметры алгоритма и состояние
кеша. Не публиковать иллюстративные числа как реальные результаты.

Для качества создать вручную проверенный небольшой набор пар с метками:
дубликат, частичный дубликат, не дубликат. Рассчитывать precision и
recall для разных порогов и параметров LSH. Отдельно сравнивать LSH с
полным перебором на небольшом корпусе. Не обещать конкретный процент
качества до проведения экспериментов.

## 13. Безопасность и надёжность

-   Никогда не удалять и не изменять исходные книги.
-   Обрабатывать некорректные пути, длинные пути, Unicode-имена,
    символические ссылки и циклы обхода согласно документированной
    политике.
-   По умолчанию не переходить по символическим ссылкам за пределы явно
    переданных каталогов, если это может создать неожиданный обход
    файловой системы.
-   Не запускать команды через shell с неэкранированными именами файлов.
-   Проверять тайм-ауты и коды завершения внешних процессов.
-   Ограничивать параллельные процессы извлечения и объём очередей.
-   Не считать частично извлечённый текст полноценным без явного
    статуса.
-   Сохранять диагностические сведения, не позволяя одной ошибке
    повредить весь индекс.
-   Не печатать огромные тексты книг в логах.

## 14. Вне рамок MVP

Не реализовывать на первом этапе:

-   автоматическое удаление, переименование или перемещение файлов;
-   полноценный GUI или веб-интерфейс;
-   сервер, сетевой API или микросервисную архитектуру;
-   встроенный OCR для сканов;
-   поиск семантических дубликатов между разными языками;
-   нейросетевые embeddings;
-   собственные полноценные парсеры для всех форматов;
-   распределённую обработку;
-   сложную систему плагинов;
-   автоматическое решение, какую из копий оставить.

Эти возможности можно рассматривать только после того, как CLI,
индексирование, поиск, тесты и benchmark работают надёжно.

## 15. Этапы реализации

### Этап 1 --- вертикальный прототип

1.  Создать CMake-проект C++20.
2.  Реализовать CLI, сканирование файлов и поддержку TXT.
3.  Реализовать нормализацию, точные хеши и базовое сравнение шинглов
    полным перебором.
4.  Добавить несколько unit-тестов и простой отчёт о совпадениях.

**Результат:** программа находит очевидные дубликаты TXT и одинаковый
нормализованный текст.

### Этап 2 --- извлечение книжных форматов

1.  Добавить интерфейс `TextExtractor`.
2.  Интегрировать Calibre через безопасный запуск внешнего процесса.
3.  Обработать тайм-ауты, ошибки, пустой результат и отсутствие Calibre.
4.  Добавить PDF-извлечение напрямую только если это оправдано качеством
    или ограничениями Calibre.
5.  Задокументировать ограничения OCR.

**Результат:** можно индексировать реальную библиотеку в доступных
форматах.

### Этап 3 --- алгоритм сходства

1.  Реализовать MinHash.
2.  Реализовать LSH и генерацию пар-кандидатов.
3.  Добавить точную проверку кандидатов и метрики.
4.  Сравнить LSH с полным перебором на тестовых данных.
5.  Добавить CSV-отчёт.

**Результат:** программа обнаруживает вероятные копии с небольшими
различиями и сообщает степень сходства.

### Этап 4 --- многопоточность

1.  Реализовать и протестировать фиксированный ThreadPool.
2.  Добавить ограниченную очередь задач.
3.  Параллелить извлечение, нормализацию и построение сигнатур.
4.  Организовать согласованную запись результатов в SQLite.
5.  Проверить одинаковость логических результатов в однопоточном и
    многопоточном режимах.
6.  Провести benchmark с разным количеством потоков.

**Результат:** надёжная многопоточная обработка с измеримым эффектом.

### Этап 5 --- постоянный индекс

1.  Добавить SQLite и версию схемы.
2.  Сохранять метаданные файлов, хеши, сигнатуры и статусы.
3.  Реализовать инкрементальную индексацию.
4.  Обработать удалённые/изменённые файлы и смену параметров
    нормализации.
5.  Добавить `stats` и интеграционные тесты.

**Результат:** повторный запуск не обрабатывает заново неизменённую
библиотеку.

### Этап 6 --- подготовка портфолио

1.  Привести README к состоянию, достаточному для запуска без помощи
    автора.
2.  Добавить схему архитектуры и описание алгоритмов.
3.  Зафиксировать результаты тестирования качества и производительности.
4.  Настроить CI.
5.  Проверить чистую сборку из нового каталога.
6.  Указать ограничения и известные проблемы.

**Результат:** законченный репозиторий, который можно демонстрировать на
собеседовании.

Этапы можно корректировать, если ранние эксперименты покажут, что
какая-то библиотека или архитектурное решение не подходит.

## 16. Требования к работе Codex

Работай с этим документом как с основной спецификацией проекта.

1.  Сначала изучи существующее содержимое репозитория. Не перезаписывай
    файлы без необходимости и не предполагай, что репозиторий пуст.
2.  Составь краткий план ближайшего этапа и предложи структуру проекта.
3.  Реализуй проект небольшими проверяемыми шагами, начиная с
    вертикального прототипа, а не со всей спецификации сразу.
4.  Перед добавлением новой зависимости объясни, зачем она нужна; не
    добавляй зависимости, которые не используются.
5.  После каждого значимого шага собирай проект и запускай релевантные
    тесты. Исправляй регрессии до перехода к следующему шагу.
6.  Не заменяй реальные реализации заглушками, которые выглядят
    завершёнными. Если функциональность пока не реализована, явно укажи
    это.
7.  Не добавляй функции вне рамок MVP без согласования.
8.  Не меняй публичный интерфейс CLI, схему БД или архитектурные решения
    с существенными последствиями без краткого объяснения причин.
9.  Учитывай безопасность файлов: исходные книги должны оставаться
    нетронутыми.
10. Пиши идиоматичный C++20: RAII, ясное владение ресурсами,
    const-correctness, минимизация глобального состояния, понятные
    ошибки.
11. Не оптимизируй преждевременно. Сначала корректность и измерения,
    затем оптимизация.
12. В конце каждого этапа сообщай: что сделано, какие файлы изменены,
    какие команды сборки/тестов выполнены, что получилось, известные
    ограничения и следующий разумный шаг.
13. Если спецификация неоднозначна, выбери простое решение, которое
    сохраняет цели проекта, и зафиксируй допущение. Задавай вопрос
    только тогда, когда неоднозначность существенно влияет на
    архитектуру, безопасность или объём работы.

**Первое действие:** проверь репозиторий и окружение, затем предложи
план реализации только Этапа 1. Не переходи сразу к полной реализации
всех этапов.
